When building payment systems for a platform handling other people's money, the architecture must shift from a "simple state update" to a "Financial Ledger" approach.

The biggest mistake developers make is just adding a is_paid = True boolean to the Order model. If a payment fails, or if a customer disputes a charge, a simple boolean gives you zero auditing power.

To make this secure, optimized, and ready to handle COD, Stripe, GCash, and PayMongo simultaneously, we create a dedicated payments app. Every time a customer attempts to pay, we record a Transaction. If it fails, we keep the record. If they try again and succeed, we record a new one.

Here is the production-grade, highly auditable schema for the payments app:

App 5: The payments App
Python
# payments/models.py

import uuid
from django.db import models
from orders.models import Order

class PaymentMethod(models.TextChoices):
    COD = 'COD', 'Cash on Delivery'
    STRIPE = 'STRIPE', 'Stripe (Card/Digital)'
    PAYMONGO = 'PAYMONGO', 'PayMongo (GCash/Maya/Card)'
    WALLET = 'WALLET', 'Internal Sarig Wallet' # Future-proofing

class PaymentStatus(models.TextChoices):
    PENDING = 'PENDING', 'Pending/Awaiting Payment'
    AUTHORIZED = 'AUTHORIZED', 'Authorized (Funds held, not captured)'
    SUCCESS = 'SUCCESS', 'Payment Successful'
    FAILED = 'FAILED', 'Payment Failed'
    REFUNDED = 'REFUNDED', 'Payment Refunded'

class PaymentTransaction(models.Model):
    # UUID for security, just like Orders
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)

    # ForeignKey, NOT OneToOne. A user might fail a card payment,
    # then try again with a different card. We want to log both attempts.
    order = models.ForeignKey(Order, on_delete=models.PROTECT, related_name='payment_attempts')

    amount = models.DecimalField(max_digits=10, decimal_places=2)

    payment_method = models.CharField(max_length=20, choices=PaymentMethod.choices, db_index=True)
    status = models.CharField(max_length=20, choices=PaymentStatus.choices, default=PaymentStatus.PENDING, db_index=True)

    # --- External Provider Tracking ---
    # This stores the Stripe PaymentIntent ID (pi_12345) or PayMongo Payment ID (pay_67890)
    # It must be indexed so Webhooks can find it instantly.
    external_transaction_id = models.CharField(max_length=255, blank=True, null=True, db_index=True, unique=True)

    # THE LIFESAVER: A JSONField to dump the exact response received from Stripe/PayMongo.
    # If a bug happens in production, you can look at this raw data to see exactly why it failed.
    provider_raw_response = models.JSONField(blank=True, null=True)

    # --- Timestamps ---
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    def __str__(self):
        return f"{self.payment_method} - {self.status} - ₱{self.amount} (Order: {str(self.order.id)[:8]})"
Why This is "Enterprise-Secure" & Optimized:
The provider_raw_response (JSONField): This is the secret weapon for production debugging. When Stripe or PayMongo sends a webhook saying a payment failed due to "insufficient funds," you dump that entire JSON payload directly into this field. If a customer complains, you don't have to guess; the exact error from the bank is saved right there.

external_transaction_id Uniqueness: By making the Stripe/PayMongo reference ID unique=True and db_index=True, you prevent "Double Spend" bugs. If a webhook fires twice by accident (which happens often with third-party APIs), the database will reject the duplicate attempt.

Separation of Concerns: The Order model knows what was bought. The PaymentTransaction model knows how it was paid for.

The Execution Flow (How the App Behaves)
Scenario A: Cash On Delivery (COD)

Customer taps "Checkout via COD" in Flutter.

Django creates the Order (Status: PENDING).

Django creates a PaymentTransaction (Method: COD, Status: PENDING).

The Rider delivers the food and taps "Payment Received" on their app.

Django updates the Order to DELIVERED and the PaymentTransaction to SUCCESS.

Scenario B: GCash via PayMongo / Card via Stripe

Customer taps "Checkout via GCash" in Flutter.

Django creates the Order (Status: PENDING).

Django creates a PaymentTransaction (Method: PAYMONGO, Status: PENDING).

Django pings the PayMongo API to generate a checkout URL and saves the resulting PayMongo ID into external_transaction_id.

Customer completes the GCash payment on their phone.

The Webhook: PayMongo sends a silent background POST request (a Webhook) to your Django server saying "Payment Success."

Django finds the PaymentTransaction using the external_transaction_id, marks it SUCCESS, and updates the Order to ACCEPTED.

This setup guarantees that even if the customer's phone loses internet connection right after paying GCash, the server-to-server Webhook catches the payment and ensures the restaurant gets the order.
